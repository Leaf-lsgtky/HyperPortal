# 荣耀「GIF 动图拖拽」机制研究与移植可行性分析

> 调研日期：2026-11-05
> 样本：`honor/荣耀任意门-17.26.9.301(172609301).apk`、`honor/framework-magic.jar`、`honor/framework.jar`、`honor/services-magic.jar`
> 工具：dexsql（DEX 反编译 / 交叉引用）+ aapt2（资源文案）
> 目标：弄清「拖拽动图后，相册里保存下来的也是动图」是怎么做到的，并判断 ohmyAES 能不能搬。

---

## 0. 结论摘要

荣耀这套能力不是"一个开关"，而是三层结构，缺一层就退化成静图：

| 层 | 位置 | 干什么 | 关键点 |
|---|---|---|---|
| **L1 采集层** | `framework.jar` 的 `hihonor.android.view.contentprocess.**`（注入到**拖拽源 App 进程**） | 长按识别视图内容，产出 `CustomDragContent` | 动图时 **payload 是 uri，不是 Bitmap**；首帧只用来做拖影 |
| **L2 规范化层** | 任意门 APK（`com.hihonor.hnmagicportal`） | 把 http 动图 / 动画 WebP **落地成本地 .gif 文件** | `FastGifConverter` + 魔改 ffmpeg-kit（`StickerConverter`） |
| **L3 消费层** | 任意门 APK `DockInfoProcessUtil` / `ServiceLogicUtil` | 白名单应用条，点击时把 payload **换成 gif 文件 uri** | `GIF_DRAG_APP_LIST`（11 个 appclip id）+ `getGifUri()` |

移植判断：

| 能力 | 可行性 | 结论 |
|---|---|---|
| 动图识别（源侧） | **高** | 我们已有 uri + mime + `sniffMime`，补 magic-byte 判定即可 |
| 首帧做拖影、uri 做 payload | **高** | ohmyAES 架构天然支持，只是现在被 PNG 重编码吃掉了 |
| 原字节跨进程搬运 | **中高** | `PortalFileProvider` 已有 `incoming/` 可写命名空间，AES 可直接写入 |
| 保存到相册仍为动图 | **高** | 只需走「拷字节 + `image/gif`」，不要 `bmp.compress` |
| 分享给第三方仍为动图 | **高** | `PortalService.dispatchImageShare()` 已经是 uri + mime 模式 |
| 动画 WebP → GIF 转码 | **低** | 需要 ffmpeg（15 MB）或自写编码器，**不建议照搬** |
| 全应用覆盖 | **中** | 荣耀自己也只覆盖「图库、微信、抖音及小红书部分页面」 |

**结论：值得做。而且我们不需要荣耀那套 ffmpeg + 框架插件体系——核心只是"别把动图降级成 PNG"。**

## 2. L1：采集层在**源 App 进程内**，payload 是 uri

### 2.1 代码归属（先分清哪些在框架、哪些在 APK）

对 `honor/framework-magic.jar` 与 `honor/framework.jar` 逐 dex 做 ASCII 扫描：

| 包 | `framework-magic.jar` | `framework.jar` | 任意门 APK |
|---|---|---|---|
| `android.hncontentrecognizer.*`（`ViewInfo`、`IHnContentRecognizerManagerService`） | classes.dex ✅ | classes2/6.dex ✅ | 引用 |
| `hihonor.android.view.contentprocess.*`（TouchHelper / DragStrategy / viewprocess / plugin 契约） | classes2.dex ✅ | ❌ | 部分重打包 |
| `hihonor.android.view.contentprocess.plugin.processor.*`（FlareUI / Compose / Emoji / Image …） | ❌ | ❌ | ✅ |
| `com.hihonor.hntransgate.**`（任意门本体） | ❌ | ❌ | ✅ |

也就是说：**真正干活的提取器是"框架注入到每个 App 进程"的**，而不是在任意门进程里远程操作别人的 View 树。

### 2.2 注入与调度链

```text
com.hihonor.android.hwcontrol.HwWidgetFactoryImpl.getContentDeliverer()
        ↓
hihonor.android.view.contentprocess.ContentDelivererImpl.createInstance()
        ↓
TouchHelper（拦截长按 / 触摸）
        ↓
strategy.ContentProcessStrategy / strategy.DragStrategy
        ↓
plugin.ContentProcessorManager.getContentProcessor()   ← 核心
```

`ContentProcessorManager` 的加载方式非常"荣耀"——**它去反射别人的 APK ClassLoader**：

```text
log: "Failed to get LoadedApk for MagicPortal"
log: "Failed to get ClassLoader for MagicPortal"
log: "Loaded plugin by LoadedApk ClassLoader: "
log: "Plugin class not found: "
class name: "hihonor.android.view.contentprocess.plugin.ContentProcessorImpl"

```

即：系统框架在**每一个 App 进程**里，通过 `LoadedApk` 拿到"荣耀任意门"APK 的 `ClassLoader`，把 `ContentProcessorImpl` 及其 processor 插件加载进来跑。所以同一份提取代码既随 APK 发布，又能在全系统 App 内生效，不需要 OTA 框架。

### 2.3 统一数据模型 `CustomDragContent`


**"动图保存还是动图"的第一因就写在这里：动图走 `TYPE_URI`，`bitmap` 只服务拖影。**

### 2.4 动图是怎么被判定的

三条判定路径，都能定位到具体代码：

**(a) FlareUI 宿主视图（ArkUI / 跨端自绘页面）**

```text
FlareUIHostViewExtractor.extract(view, x, y, ViewInfo)
    ↓ getLocationOnScreen → 局部坐标 → findBestHit(list, …) 命中内容节点
    ↓ props.toString().contains("TextRenderProps")  → extractText
    ↓ props.toString().contains("ImageRenderProps") → extractImage
FlareUIHostViewExtractor.extractImage(...)
    ↓ tryExtractImageUrl(props)       // 从 "source=Uri:content://…" / "source=Network:https://…"
    ↓ isGifNode(url, nodeKey)         // ★
    ↓ 屏幕尺寸 < 200x200 直接放弃
    ├─ true  → buildGifContent(...)
    └─ false → buildImageContent(...)
```

`isGifNode(String url, String nodeKey)` 判定极简单：

```java
url.toLowerCase().contains(".gif") || url.toLowerCase().contains(".heif")
   || (nodeKey != null && nodeKey.contains("gif_image"))
```

`.heif` 也当动图——对应动态照片 / 动画 HEIF。

`buildGifContent` 落库：

```java
type      = 2;              // TYPE_URI
uri       = Uri.parse(url);
mimeType  = "image/gif";
viewType  = "gif";          // ← 后面会成为 ClipData label
bitmap    = captureRegionFromView(view, captureRect);
shadowBitmap = bitmap;      // 同一个 Bitmap，只做拖影
log: "buildGifContent: uri=… shadow=WxH"
```

**(b) Compose 应用（抖音 / 小红书）**

```text
ComposeViewAwemeProcessor.resolveImage(Object entry, Rect bounds, long deadline)
    ↓ 顺着 Compose 树找 PainterElement → findPainterField → scanPainterForImage
    ↓ isAnimatedDrawable(painter 类名)：含 AnimatedDrawable / AnimatedImage /
                                        GifDrawable / MovieDrawable
    ├─ animated && uri != null → ExtractResult.uri(uri, animated=true, firstFrameBitmap)
    │      log: "resolveImage: animated -> uri …"
    │      log: "resolveImage: shadow use bitmap WxH" / "shadowBitmap(animated frame)"
    └─ 否则 → 抠 Bitmap，裁 opaqueBoundingBox 后回传
           log: "resolveImage: bitmap WxH (animated first frame)" ← 只有这种情况退回首帧
```

`extractContent` 里把 `viewType` 设为 `"compose"`。这个 `"compose"` 后面会被任意门用来识别"http 动图"（见 §3.2）。

**(c) 表情 / 表情包（微信、抖音、小红书）**

框架里的 `viewprocess/EmojiViewProcessor` 有**按 App 定制**的三个方法：

```text
getWechatEmojiUrl(View)   // 91 opcodes
getAwemeEmojiUrl(View)    // 96 opcodes
getXhsEmojiUrl(View)      // 77 opcodes
```

`getWechatEmojiUrl` 的逻辑（以微信为例）：

```text
1. 用 ViewInfo.getPath() 拿到的**类名**，在 view 及其父类（最多 10 层）的
   declared field 里找"值类型类名 == path"的那个字段 → 即 EmojiInfo 对象
2. getFieldRecursively(emojiInfo, ViewInfo.getField()) 取出 String 字段
3. 该 String 就是表情的 gif/webp url
```

APK 侧还有一份同名的 `plugin/processor/EmojiViewProcessor.getGifMakerEmojiUrl`，走的是另一条：

```text
view.<ViewInfo.getTarget()>()      // 反射调用无参方法 → DraweeController
   → <ViewInfo.getTargetField()>()  // → DataSource
   → findHttpUriFromDataSource()    // 一路挖出 http url
```

失败时 log 很直白：`"getGifMakerEmojiUrl: draweeController is null" / "…no emoji url found"`。

**关键：`ViewInfo` 的 `path` / `field` / `target` / `targetField` 这些"反射路标"不是硬编码，而是由系统服务下发的按包配置**（`IHnContentRecognizerManagerService.getPackageConfigs(pkg)` / `getPackageAllConfigs(pkg, activity)` / `getWhiteActivityConfig`）。APK 只在 assets 里有 `app_functions_v2.xml`（那是 AppFunctions/LLM 工具 schema，不是拖拽规则）。也就是说**微信/抖音/小红书的反射路标是可云控的**，这也是荣耀"部分页面"的由来。

### 2.5 跨进程交付：动图字节怎么从源 App 到任意门

这是全链路里最难、也最值得学的一环。**任意门进程打不开微信的私有 `content://`**，所以荣耀在**源 App 进程内**就把字节交出去了。

`DragStrategy.buildCustomClipData(view, content, viewType)`：

```java
int type = content.type;

if (type == 1) {                      // TYPE_IMAGE_BITMAP
    uri = HnRecognizerManagerUtils.getUriForBitmap(bitmap, pkg);
    return new ClipData(viewType, new String[]{"image/*"}, new Item(uri));
}

if (type == 2) {                      // TYPE_URI ← 动图走这条
    String mime = content.mimeType != null ? content.mimeType : "*/*";
    Uri uri = content.uri;
    if ("image/gif".equals(mime) && uri != null) {
        Uri emoji = buildEmojiUri(uri.toString(), pkg);   // ★
        if (emoji != null) uri = emoji;
        else {
            log: "buildCustomClipData: gif uri resolve null, use raw uri";
            // 退路：把首帧 Bitmap 也塞成第二个 item
            extra = getUriForBitmap(content.shadowBitmap, pkg);
        }
    }
    ClipData cd = new ClipData(viewType, new String[]{mime}, new Item(uri));
    if (extra != null) cd.addItem(new Item(extra));
    return cd;
}

if (type == 3) { /* 实况照片：getLivePhotoUri → mime {"image/*","image/livephoto"} */ }
```

`buildEmojiUri(String src, String pkg)` 分三种情况，全部在源进程内完成：

```text
file://xxx        → ParcelFileDescriptor.open(file, MODE_READ_ONLY)
                  → HnRecognizerManagerUtils.getEmojiUriByFd(pfd, fileName, pkg)
http(s)://...     → HnRecognizerManagerUtils.getEmojiUri(url, pkg, fileName)
纯路径            → 同 file://
```

对应的 Binder 契约（`android.hncontentrecognizer.IHnContentRecognizerManagerService`）：

```text
dumpGifByDescriptor(ParcelFileDescriptor pfd, String name, String mime) → Uri   ★ 动图专用
dumpFileByFileDescriptor(ParcelFileDescriptor pfd, String name, String mime, String label) → Uri
dumpFileByNetWork(String url, String pkg, String mime) → Uri
dumpFile(Bitmap bmp, String label) → Uri
isSupportGifDrag() → boolean        ★ GIF 能力总闸
getPackageConfigs / getPackageAllConfigs / getWhiteActivityConfig / getBlackActivityConfig
isContentRecognizerEnable / isPackageEnable / isGlobalDragEnabled / isSupportDragEnabled
reportDragByMistake / showSetDragFunctionTip / getCloudConfigsBundle
```

**本质：源 App 进程通过 `ParcelFileDescriptor` 把真文件句柄递给系统服务，服务落到自己可被任意门读的 provider 里，返回一个 `content://` uri。** 这条链保证了动图字节一路无损。

顺带一个细节：动图的 `ClipData` label 是 `viewType`，所以分别出现 `"gif"`（FlareUI）、`"compose"`（Compose）、`"image"`（表情路径，见下）。label 本身承担了"来源类型"语义。

## 3. L2：任意门侧——识别、规范化、换载荷

### 3.1 判定"这次拖的是动图"

```java
// DockInfoProcessUtil
private boolean needCreateGifDockItem(Context ctx, ClipData data) {
    if (data == null || data.getItemAt(0) == null) return false;
    Uri uri = data.getItemAt(0).getUri();
    if (uri == null) return false;
    String mime = ctx.getContentResolver().getType(uri);
    if (!TextUtils.isEmpty(mime) && CommonUtils.MotionType.GIF.mimeType.equals(mime))
        return true;                       // 本地动图：image/gif
    return isHttpGifClipData(ctx, data);    // 远程动图
}

private boolean isHttpGifClipData(Context ctx, ClipData data) {
    // 1. item[0].uri 的 scheme 必须是 http / https
    // 2. ClipDescription.getLabel() 必须等于 "compose"
    // 3. ClipDescription.getMimeType(0) 必须等于 "image/gif"
}
```

`label == "compose"` 这个条件非常值得注意：**荣耀信任"自家 Compose 提取器产生的 http gif 拖拽"**，别家 App 发起的同名 label 拖拽会被一并接住（也算一种弱鉴权）。

调用点在 `createDockItemInfos()` / `createDefaultItemInfos()`。`createDockItemInfos` 里的实际条件（逐字）：


能对上号的 id：

| appClipId | 含义 | 依据 |
|---|---|---|
| `237321902018789376` | 相册（图库） | `moveGalleryServiceToFirst()` 里与"微信好友"并列提升到首位，日志 `gallery or wechat friend service not found` |
| `101031071591694336` | 微信好友 | 同上 |
| `80316A39-70B7-7CA5-493E-286A73790195` | 收藏空间 | `getDefaultCollectCenterService()` / `TransGateConstants` / 设置页 `CustomServiceFragment` |
| `402827255241244672` | 预置默认拖拽服务 | `iconcache/HispInfoManager` + `GIF_DRAG_APP_LIST` 双处出现 |
| `500689412057726976` | 预置默认拖拽服务 | `TransGateConstants` + `GIF_DRAG_APP_LIST` 双处出现 |
| 其余 6 个 | 由 Hisp 服务运行时下发 | APK 内无映射；其中 5 个在 `assets/<id>.png` 有预置图标，说明是内置服务 |

**结论：白名单是 appclipId 硬编码，标签/图标来自 `com.hihonor` 的 Hisp 图标服务；这套 id 无法在小米机型上复用。**

### 3.3 规范化：把 http 动图 / 动画 WebP 变成真 `.gif` 文件

```java
// DockInfoProcessUtil.updateGifCovertUri(ctx, clip, item)
if (isHttpGifClipData(ctx, clip))
    FastGifConverter.convertFromUrl(ctx, item.getUri().toString(),
                                    buildHttpGifCallback(ctx, clip, CommonUtils.getsTraceID()));
else if (needCreateGifDockItem(ctx, clip))
    FastGifConverter.convert(ctx, item.getUri(),
                             buildLocalGifCallback(ctx, CommonUtils.getsTraceID()));
```

```java
// FastGifConverter.convert / convertFromUrl（两个 R8 lambda 实现）
clearGifDirectory(ctx);                                     // 清空 cacheDir/gifFiles
File src = copyUriToFile(ctx, uri);  // 或 downloadToCache(ctx, url)
File dst = new File(cacheDir/gifFiles, "mp_gif_" + System.currentTimeMillis() + ".gif");
StickerConverter.convertToGif(src, dst, ConvertOptions.balanced(), callback);
```

`StickerConverter`（`com.arthenica.ffmpegkit.sticker`，**魔改版 ffmpeg-kit**）：

```java
detectFormat(path):    // 读前 12 字节
    "RIFF" + [8..11]=="WEBP" → 1   (WEBP)
    [4..7]=="ftyp"           → 2   (HEIF/MP4 容器)
    其他                      → 0

convertToGif(src, dst, opts, cb):
    format==1 → convertWebpToGif(...)     // 专用路径
    否则       → convertWithFfmpeg(src, dst, -1, opts, cb)
```

动画 WebP 专用路径（因为 ffmpeg 的 webp 解复用对表情包不友好）：

```text
nativeExtractWebpFrames(srcPath, framesDir, maxWidth) → JSON {"frames":N,"durationMs":M}
    失败 → 回落 convertWithFfmpeg
    N==0 → onFailure("No frames found in WebP file")
写 concat.txt
ffmpeg -f concat -safe 0 -i concat.txt -filter_complex <FILTER> -f gif -y out.gif
```

`ConvertOptions.balanced()` 实测取值：

```text
maxColors = 128        （构造默认 256，balanced() 覆盖成 0x80）
targetFps = 10
maxWidth  = 0          （0 = 不缩放）
```

拼出来的 `-filter_complex`（逐字）：

```text
[0:v]scale=<maxWidth>:-1:flags=bilinear,fps=10,format=rgba,split[s0][s1];
[s0]palettegen=max_colors=128:reserve_transparent=1:stats_mode=diff[p];
[s1][p]paletteuse=dither=none:diff_mode=rectangle:alpha_threshold=128
```

（`maxWidth==0` 时 `scale=` 那段会被省略，即原始分辨率 + 10 fps + 128 色调色板 + 保留透明。）

转换成功回调（`DockInfoProcessUtil$2.onSuccess`）：

```java
if (!traceId.equals(CommonUtils.getsTraceID())) { log: "convert onSuccess dropped: traceId changed"; return; }
Uri gifUri = FileProvider.getUriForFile(ctx, "com.hihonor.hntransgate.fileprovider", new File(path));
applyConvertedUri(gifUri);       // sContentUri = uri; mUriList[0] = uri; mContent = "[uri]"
log: "convert success, uri=" + sContentUri
```

`traceId` 是"这一次拖拽"的代次号：拖拽结束/新拖拽开始就换号，迟到的转换结果直接丢弃。**这是必须学的并发保护**。

另外 `downloadToCache` 有体积上限，超了直接放弃：

```text
log: "download gif too large: "
log: "download gif failed, response code: "
```

## 5. 五个值得直接抄的设计洞察

1. **动图的 payload 永远不经过 Bitmap。** 首帧 Bitmap 只服务拖影（`shadowBitmap`）。一旦用 Bitmap 当载荷，动图就必然退化。
2. **字节搬运必须在源 App 进程完成。** 靠 `ParcelFileDescriptor` 过 Binder，而不是"目标进程去读别人的 content://"。这是全链路最关键的一条。
3. **规范化（WebP→GIF、http→本地）放在中间层，且异步。** 转换和拖拽并行，拖完立刻可用；`traceId` 防止上一轮结果污染下一轮。
4. **消费端用白名单而不是"全试一遍"。** 因为"哪个 App 真的能吃 image/gif"无法可靠探测，荣耀选择硬编码 11 个 + 明确声明覆盖不全。
5. **每次拖拽一个代次号（traceId）。** 迟到的异步结果必须能被丢弃，否则会把上一次的图错发给这一次的目标。

### 6.2 逐环节可行性评分

| 环节 | 难度 | 说明 |
|---|---|---|
| 动图判定（GIF87a/89a、RIFF+WEBP+ANIM、ftyp heic/heif、APNG acTL） | ★☆☆☆☆ | 加一个 12 字节 magic 判定，和荣耀 `detectFormat` 同级 |
| 源进程把原字节写入 `PortalFileProvider` `incoming/` | ★★☆☆☆ | provider 已可写；需带 mime + 扩展名，注意 5–20 MB 的体积 |
| 拖影仍用首帧 | ★☆☆☆☆ | 已经这样 |
| 保存到相册保留动图 | ★★☆☆☆ | `MediaStore` 插入 + 拷字节 + `IS_PENDING`，绕过 `bmp.compress` |
| 分享给第三方保留动图 | ★★☆☆☆ | `dispatchImageShare` 不动，只把 uri 换成 gif 副本 |
| 剪贴板保留动图 | ★★★☆☆ | 直接 `ClipData.newUri(cr, "image", gifUri)`；HyperOS 剪贴板对 gif 的支持需实测 |
| 中转站（传送门保存） | ★★★☆☆ | 需要 file 级 API，现只有 `saveBitmap`；要么扩展 Manager，要么另存一份文件条目 |
| 动画 WebP → GIF 转码 | ★★★★☆ | **不建议**：ffmpeg-kit 全套 ≈15 MB；Android 无内置 GIF 编码器 |
| 应用条过滤 | ★★☆☆☆ | 用 `PackageManager` 反查「谁声明了 `image/gif`」比硬编码白名单更好 |

### 6.3 推荐实施方案

**Phase 1（1 天级，收益最大）——停止降级**

1. 新增 `AnimatedImages.isAnimated(ParcelFileDescriptor|Uri|byte[])`：
   - `GIF87a` / `GIF89a`
   - `RIFF` + `WEBP` + 第 12–15 字节为 `VP8X` 且扩展块含 `ANIM`
   - `ftyp` + brand ∈ {`heic`,`heix`,`mif1`,`msf1`,`avif`}（动态照片）
   - APNG：`PNG` 后出现 `acTL` 块
2. `PortalFileProvider` 增加 `stageStream(Uri src, String name, String mime)`：把原始字节写进 `incoming/`，返回 uri。
3. `PortalSystemUiModule`：
   - `mImageAnimated && mImageUri != null` → 走原字节（由 AES 在源进程写入），否则维持现状 PNG。
   - `saveImageToGallery`：动图分支 → `MediaStore` + `copyStream`，`MIME_TYPE=image/gif`。
   - `copyImageToClipboard`：动图分支 → `ClipData.newUri(cr, "image", gifUri)`。
4. `AES/Bridge.java`：`openPfd` 成功后先记录 `mime` + `isAnimated` + 文件大小，随 payload 上报（`mimeType` 已有，加 `animated` / `size`）。

**Phase 2（可选）——覆盖面的提升**

5. 应用条按能力过滤：`PackageManager.queryIntentActivities(ACTION_SEND, image/gif)`，谁声明谁上（比荣耀白名单更合理，且不依赖任何厂商服务）。
6. 超限保护：`size > N MB`（建议 20 MB）时回退首帧 + Toast 提示，对齐荣耀的 `download gif too large`。

**Phase 3（不建议做）**

7. WebP→GIF 转码：只有当目标 App 明确不接受 `image/webp` 时才需要。微信表情本身支持动画 WebP，直接透传即可；真要转码建议内置一个 ~60 KB 的 GIF 编码器（纯 Java）而不是拖 ffmpeg。**注意专利/许可证**：ffmpeg-kit 已归档，GPL/LGPL 边界要评估。

### 6.4 风险与坑

| 风险 | 说明 | 对策 |
|---|---|---|
| **体积** | 动图 5–20 MB，跨进程拷贝 + 相册插入都慢 | 异步 + 大小上限 + 进度提示；不要在主线程 |
| **内存** | 严禁 `ImageDecoder` 全帧解码 | 只解首帧做拖影，其余走流拷贝 |
| **权限** | SystemUI / HyperPortal 打不开源 App 私有 uri | 必须由源进程（AES）先落 `incoming/`，这正是荣耀的做法 |
| **目标 App 不认 gif** | 部分 App 对 `EXTRA_STREAM` + `image/gif` 直接崩/静默失败 | 失败即回退 PNG（保留现有路径作为 fallback） |
| **HyperOS 相册** | 需实测 `image/gif` 落 `Pictures/` 后是否被识别为动图 | 首次实现后让用户手测 |
| **剪贴板** | HyperOS 剪贴板对 gif 支持未知 | 降级为"复制首帧 + 提示" |
| **代次竞争** | 异步转换/拷贝晚于下一次拖拽 | 抄荣耀的 `traceId` 模式 |
| **适配面** | 荣耀也只覆盖图库/微信/抖音/小红书部分页面 | 不承诺全覆盖，先把"能拖出来的动图不降级"做扎实 |

### 6.5 总评

| 维度 | 评价 |
|---|---|
| 技术可行性 | **高**（不需要复刻荣耀的框架注入 + ffmpeg 体系） |
| 工作量 | 小（Phase 1 的四个改动点，全是"少做一件事"而不是"多做一件事"） |
| 用户价值 | 高（动图是本项目最常被拿来对比 ColorOS/荣耀的能力之一） |
| 依赖风险 | 低（不依赖任何厂商服务；`PortalFileProvider` 是自有组件） |
| 与现有架构冲突 | 无（`dispatchImageShare` 本来就是 uri 模式，PNG 是多余的一步） |

**一句话：荣耀用三层工程把"动图别变静图"做成了体系；我们只要把已经有的 uri 一路带到终点、不在中途 PNG 化，就能拿到 80% 的效果。**
